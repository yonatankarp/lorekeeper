# Lorekeeper sync

Shared campaigns sync between the party's computers through a small Lorekeeper sync server. The server stores only encrypted data: it can't read note contents, file names or player names. Each player's local campaign folder stays the real copy; sync replicates it, and Lorekeeper works offline and catches up later. Each member also has a private space: their `Private/` folder syncs only to their own computers (and to DMs when the owner allows it); see "Private notes".

The reference server runs on the maintainer's machine at `https://lorekeeper.yonatankarp.com`. The server address is a setting, so anyone can run their own from the published image (see "Running your own sync server").

## Pieces

| Path | What |
|---|---|
| `sync-protocol/` | Rust crate shared by the app and the server: message types, encryption, ids, invite links |
| `sync-server/` | The server (Rust, axum, SQLite), built into `ghcr.io/yonatankarp/lorekeeper-sync` |
| `src-tauri/` | The app; its sync engine uses `sync-protocol` |

`sync-protocol` is a path dependency of both (no Cargo workspace, so `src-tauri` builds as before).

## Rooms, owners, members and invites

A shared campaign that syncs is a **room** on the server.

- `room`: 16 random bytes, base32 (lowercase, no padding, 26 characters), public identifier.
- `key`: 32 random bytes, the room's encryption key. Made by the owner's app and never sent to the server.
- **Tokens**: 32 random bytes each, base64url without padding (43 characters). The server makes them and stores only `SHA-256(token)`, with a `member_id` (16 random bytes, base32), a role and a `manage` flag. There are no accounts: a member is whoever holds their token, and their identity (member id, role, private space) is what the invite they redeemed gave them.
  - The **owner token** comes back when the room is created. Its holder, the room's creator, is the only `owner`.
  - Everyone else gets a token of their own by redeeming an invite, with the invite's role.
- **Roles:** `owner` (exactly one), `dm` and `player`. A `dm` may also have `manage`. Rooms from before roles said `member`; the server reads that as `player`, and `Role` deserializes `"member"` as `player` too.
  - **Owner:** everything below, and alone: grants `manage`, changes roles (`PATCH .../members/{id}`), the room's settings (`PATCH .../settings`), and on their own member row `owner_is_dm` ("I'm also the DM", default off). Being the owner reads no private notes by itself: in many parties the owner is a player and someone else runs the game.
  - **Managers** (a `dm` with `manage`): invite players and DMs without `manage`, list and cancel invites (not one that grants `manage` or re-invites a manager: they don't even see those, since they hold the key and could redeem any invite they see), list members, and remove or re-invite members who don't manage. Never the owner or another manager.
  - **DMs and players** sync; neither administers. A DM, and an owner with `owner_is_dm`, also read the players' private notes when the room's `dm_reads_private` is on (`Role::reads_private(owner_is_dm, dm_reads_private)`).
- **Invite**: 16 random bytes, base32, made by the owner or a manager, with a role and `manage`. One-time, expires after 7 days (`LOREKEEPER_SYNC_INVITE_DAYS`). At most 32 members plus pending invites per room (re-invites don't take a seat).
- **Re-invite**: an invite bound to an existing `member_id`. Redeeming it revokes that member's tokens (their sockets close with `4002`, which the app shows as "Signed in on another computer") and gives the new token the same member id, role, `manage`, display id (unless the redeem gives one) and private space. It's how a player moves to a new computer, since tokens live in each computer's keychain. It hands over the member as they were when it was made: if their role or `manage` changed since, redeeming it gives `invite_not_found` (so a manager can't re-invite a player, wait for the owner to make them a manager, and take that manager over). The owner can't be re-invited (the owner token stays on the computer that shared the campaign). Whoever redeems a re-invite becomes that member, private notes included, so the owner and managers can, in principle, take over a player's identity this way; the player then sees "Signed in on another computer".
- **Room setting** `dm_reads_private` (default off), set by the owner only: DMs (and the owner, if they said they're the DM) receive every member's private notes.

**Invite link:** `https://lorekeeper.yonatankarp.com/join/<room>/<invite>#<key>` (key base64url, no padding). The part after `#` never reaches the server (browsers and HTTP clients don't send fragments), and no token travels in links. The server answers `GET /join/<room>/<invite>` with a small page that hands the link to the app (see "Opening an invite from the browser"), with the manual way as a fallback (Settings > General > Join a shared campaign, paste the link); showing the page doesn't use up the invite. The app accepts the full link pasted into its Join dialog, redeems the invite for its own member token, and talks to the server origin in the link.

**Opening an invite from the browser:** the app registers the URL scheme `lorekeeper` (tauri-plugin-deep-link: the macOS bundle's Info.plist and the Windows installers declare it; on Linux the packages' desktop file, and the app registers itself at start for an AppImage, best effort). The deep link carries the whole invite link, URL-encoded: `lorekeeper://join?link=<encodeURIComponent(invite link)>`, so it keeps the server origin (self-hosted and `http://127.0.0.1` servers work too) and the app reads it with the same parser as a pasted link.

- **The join page** has one inline script, allowed by its hash (`script-src 'sha256-...'`, computed by the server from the script's exact text; nothing else may run). If the path is `/join/<room>/<invite>` and `location.hash` is `#` plus 43 base64url characters, it builds `lorekeeper://join?link=` + `encodeURIComponent(location.origin + location.pathname + location.hash)`, puts it on the page's **Open in Lorekeeper** button, and navigates to it (`location.replace`), so the browser asks "Open Lorekeeper?". The fragment goes nowhere else: no request, no logging, no storage, and the page loads nothing (`default-src 'none'`, `base-uri 'none'`, `form-action 'none'`, `frame-ancestors 'none'`, `nosniff`, `no-referrer`). Its other links are **Download Lorekeeper** (`https://yonatankarp.com/lorekeeper/`) and the manual instructions. A browser that doesn't know the scheme (Lorekeeper isn't installed) may show an error, or in Firefox replace the page with one; Back returns to it.
- **The app** treats a deep link as hostile input from any web page (`deeplink.rs`): at most 2048 bytes; exactly `lorekeeper://join?link=` followed only by unreserved characters and `%XX` (no other parameter, no fragment); strict percent-decoding to UTF-8; then `Invite::parse`. It never joins, opens another URL or runs anything: it brings the Settings window forward and opens **Join a shared campaign** (also on a fresh install with no campaign yet) with the link filled in and checked (its server shown, with the warning when it isn't the default), and the player still clicks **Join**. A malformed one opens the dialog with "That Lorekeeper link isn't an invite link". Lorekeeper never puts the link, which holds the key, in an event of its own: the window is told to ask and takes it, once, with `take_join_link` (refused for any other window). The deep-link plugin itself emits the URL as `deep-link://new-url` to every window and keeps the last one in memory until the app quits. No window listens to that event, but the app's own windows (main, capture, settings) could, as they can any event (`core:default`); the D&D Beyond window can't (it has no capability, so no IPC at all). No window has the plugin's permissions (`deep-link:*`), so none can read the kept one. The last link wins; one arriving while a join is running is dropped. On Windows and Linux each link starts a new process, so tauri-plugin-single-instance hands it to the running copy, which keeps it from a second copy starting.
- **Test profiles** (`LOREKEEPER_PROFILE`) ignore deep links and don't take part in single-instance (two copies can't both own the scheme): paste the link instead.

Link parsing is strict (`Invite::parse`): `https://host[:port]` (plain `http://` only for `localhost`, `127.0.0.1` and `[::1]`), exactly `/join/<room>/<invite>`, no user info, query or trailing slash, and a 32-byte key. Surrounding whitespace is ignored and the host is lowercased.

Anyone with an unredeemed link can join once, so the owner shares it only with the party. Lorekeeper keeps `key` and the token in the OS keychain, never in settings files or notes.

**Member display id**: an opaque string a client chooses, sent when redeeming and in `hello`. Clients should send their PC name encrypted with the room key, so only the party can read it (Lorekeeper sends `DM` for a DM who plays no character); the server only stores and relays it (up to 512 bytes).

**Migration:** the server's database carries `PRAGMA user_version`. Version 1 adds `rooms.dm_reads_private`, `tokens.manage`, `invites.role`, `invites.manage` and `invites.member_id`, turns `member` into `player`, and rebuilds `files` with an `owner` column (`''` for every existing file, which stays shared) in the primary key `(room, owner, id)`. Version 2 adds `tokens.owner_is_dm` (off for every existing owner). Each runs once, in its own transaction, when the server opens the database. Existing rooms keep their owner; existing members become players; `dm_reads_private` starts off.

## Encryption

- **File id:** `id = base32(BLAKE3-keyed(key, "lorekeeper file id v1" || path)[..16])`, where `path` is the file's path inside the campaign folder with `/` separators (e.g. `Sessions/Session 4/Sibling 5.md`) as UTF-8. Stable per path, unguessable without the key.
- **Private file id:** `base32(BLAKE3-keyed(key, "lorekeeper private file id v1" || member_id || path)[..16])` (`private_file_id`), where `member_id` is the author's (26 ASCII characters) and `path` is relative to their `Private/` folder (`Private/NPCs/Vex.md` has the path `NPCs/Vex.md`). The context differs from the shared one at byte 12, so no private id equals a shared one, and the member id makes two members' identical private paths different ids: the server can link a private file neither to a shared page nor to another member's private file. The blob of a private file holds that inner path, and `open_private` checks it against the id for the author the change names, so a server can't pass a private blob off as shared, as another member's, or the other way round.
- **Blob:** `XChaCha20-Poly1305(key, random 24-byte nonce)` over the JSON `{"path": "...", "content": "<base64>", "modified": <unix ms>}` (fields in that order, `content` in standard base64 with padding); stored as `nonce || ciphertext || 16-byte tag`, and sent as standard base64 with padding. The AEAD's associated data is the room string followed by the id string (their 26 ASCII characters each), so a blob can't be moved to another file or room.
- **Encrypted tombstone:** a client deletes a file by writing a normal blob whose JSON is `{"path": "...", "content": "", "modified": <unix ms>, "deleted": true}` (`FileContent::tombstone`). The `deleted` field is left out of ordinary blobs, so their layout is unchanged. Clients never use the server's own delete (a null blob): it carries nothing sealed with the key, so anyone with a token could send one.
- **Member display id:** `base64(nonce || XChaCha20-Poly1305(key, nonce, name))` with associated data `room || "lorekeeper member name v1"` (`seal_member`, `open_member`): the player's character name, at most 300 bytes, "" for none.
- **Content hash** for change detection, computed by clients only: BLAKE3 of the plain bytes, lowercase hex.
- **Opening a blob** (`open`) also checks the path inside, since every party member holds the key and can seal anything: it must be relative and stay in the campaign folder (no empty, `.` or `..` components, no leading `/`, no `\`, NUL or drive prefix like `C:`), and the blob's file id must be the one derived from it. A blob that fails either check is treated like one that doesn't decrypt.
- **What the key doesn't protect:** the server can't check blobs, so anyone holding a token (a member, or someone who stole a token without the key) can overwrite a file with garbage or delete it (a tombstone carries no blob). They can't read or forge content. Clients should treat a blob that doesn't open as a conflict, not as new content.

`sync-protocol` has known-answer tests for the file id and the blob layout; changing either breaks every synced campaign.

## Sync channel (WebSocket)

`GET /v1/rooms/{room}/live` upgrades to a WebSocket. It is the one way clients read and write room contents: catch-up, live changes, writes and presence all go over it. The connection stays open; when it drops, the client reconnects and says `hello` with the last `seq` it has.

**Auth** on the upgrade request, owner or member token (checked again, by the token itself, once the socket has its place in the room, so a re-invite racing the upgrade can't leave the old token connected): `Authorization: Bearer <token>` (preferred). Clients that can't set headers on an upgrade (browsers) can instead offer the subprotocols `lorekeeper, token.<token>` (the server answers with `lorekeeper` and never echoes the token). A token in the URL (`?token=`) is never read, since URLs end up in proxy logs. A wrong, revoked or missing token, or an unknown room, gets `401` before the upgrade.

**Messages:** JSON text frames (types in `sync-protocol`: `ClientMessage`, `ServerMessage`). `seq` is one increasing counter per room; every successful write gets the next value.

Client to server:

| Message | |
|---|---|
| `{"type":"hello","since":N,"member":"<display id>","dm_since":M}` | Once, first. The server sends `access`, replays every file this member may see changed after `since` (0 for all) as `changes` batches, then sends `presence`, then streams live. Other members' private files (only for those who read them) replay after `dm_since` instead when it's given (optional). |
| `{"type":"put","req":R,"id":"...","base":N,"blob":"<base64>","space":"private"}` | Write a file. `base` = the `seq` the client last saw for this id (0 = new). `req` is any number the client picks to match the answer. `space` is `"shared"` (the default, left out) or `"private"`: the writer's own private space. Nothing names another member's space. |
| `{"type":"delete","req":R,"id":"...","base":N,"space":...}` | Delete a file; it keeps a tombstone (blob null) so others learn of it. |
| `{"type":"ping"}` | Answered with `{"type":"pong"}`. |

Server to client:

| Message | |
|---|---|
| `{"type":"access","member_id","role","manage","owner_is_dm","dm_reads_private","members":[...]}` | Who this connection is and what it may read: right after `hello` (before the replay, since the client needs its member id for its private files) and whenever any of it changes (a role or `manage` change, the room setting, a member joining or leaving). `members` (`[{"member_id","member","role"}]`) is there only for a member who reads others' private notes, so the app can drop copies of members no longer in the room. |
| `{"type":"changes","seq":S,"changes":[{"id","seq","blob" or null,"author"}],"more":bool,"total":T}` | Replay batch after `hello` (`seq` = the room's latest). At most 500 changes and 4 MiB of blobs per batch (always at least one change); the last batch has `more: false`. Each file appears once, at its latest version. `author` (a member id) is there for a private file: the member whose private space it's in. `total` (on every batch of the replay) is how many changes the whole replay holds, counted when it starts with the same visibility rule as the replay itself (`db::count_changes`, so it says nothing about files you may not see), for the app's progress; writes during the replay can add a few. Servers before it leave it out. |
| `{"type":"change","id":"...","seq":S,"blob":"..." or null,"author":...}` | A write by another connection, sent to every connected socket of the room that may see it, including the writer's other devices, but not to the socket that wrote it (it got an `ack`). |
| `{"type":"ack","req":R,"seq":S}` | The write is stored as `seq` S. |
| `{"type":"conflict","req":R,"seq":S,"blob":"..." or null}` | The file changed since `base`: its current version in the same space (null when deleted), for the client to resolve. For a private write that's always the writer's own private file. |
| `{"type":"presence","members":[{"member_id","member","role"}]}` | Who is connected (after their `hello`), one entry per member; sent after the replay and whenever it changes. |
| `{"type":"error","req":R,"error":"<code>"}` | A refused message; `req` is there when the message had one. The socket stays open. |

**Write rules:** a write succeeds when `base` equals the file's current `seq` in its space; for a file that doesn't exist or is deleted, `base` 0 also matches, so a file can be created again over a tombstone. Deleting a missing or already deleted file changes nothing and answers `ack` with that file's current `seq` (0 if it never existed). `put` and `delete` before `hello` get `hello_first`. The server stores a private write under `(room, writer's member_id, id)`, so two members' private files never collide and nobody can write into anyone else's space.

**Who sees what** (`db::changes`, the one place it's decided, for the replay, the live stream and `GET /changes` alike): shared files; your own private files; and other members' private files only when you read them right now (`dm`, or `owner` with `owner_is_dm`, and `dm_reads_private` on). Role, `owner_is_dm` and setting are read from the database for every page sent, never cached on the socket, so a demotion or the setting turned off stops delivery from the next page on: a page already read while access allowed it (at most 500 changes and 4 MiB of blobs) still goes out, which takes as long as that page takes to send (up to the 5-minute send timeout for a reader that stalls). A removed or re-invited member's sockets are closed mid-send instead. When a socket gains access mid-connection, the server sends it every private file it may now read. `seq` stays one counter per room: a member may see gaps where others' private writes went.

**Error codes:** `bad_message`, `hello_first`, `hello_twice`, `member_too_long`, `bad_id`, `bad_blob` (not base64, or shorter than nonce and tag), `too_large`, `room_full`, `too_many_files`, `rate_limited`, `unauthorized` (the writer was removed meanwhile), `internal`.

**Keeping it open:** the server sends a WebSocket ping every 30 seconds (Cloudflare drops connections idle for about 100 seconds) and closes a socket it hasn't heard from (any frame, pongs included) in 75 seconds. It closes sockets with code `4001` when their member is removed (or left), `4002` when a re-invite signed the member in on another computer and `4003` ("campaign deleted by its owner") when the owner deleted the room (all at once, even in the middle of a replay or a send) and, when it gets the chance, `1012` when the server shuts down; clients reconnect after `1012` or a dropped connection, after `4001` tell the player they were removed, after `4002` that they're signed in on another computer, and after `4003` that the owner stopped sharing. Frames are limited to the blob limit in base64 plus 64 KiB; a bigger frame closes the socket. More than 600 client messages in a minute on one socket close it with `1008`. A socket that doesn't take a frame within 5 minutes (a reader that stopped reading) is dropped.

## HTTP API (v1)

Plain HTTP covers room creation, invites and members, roles, the room's setting, health, the join page and an optional read. All JSON; errors are `{"error":"<code>"}`. Auth: `Authorization: Bearer <token>`; a wrong, revoked or missing token gets `401 {"error":"unauthorized"}`, the same answer for unknown rooms, so rooms can't be probed. Endpoints for managers answer anyone else with `403 {"error":"not_allowed"}`; owner-only endpoints (and a manager reaching past their rights) get `403 {"error":"owner_only"}`. Times are unix milliseconds.

| Method and path | Auth | Answer |
|---|---|---|
| `POST /v1/rooms` | creation key | `201 {"room","owner_token"}`. Needs the header `X-Lorekeeper-Create-Key: <key>` (the server's `LOREKEEPER_SYNC_CREATE_KEY`), else `403 {"error":"create_key_required"}` (the app then asks for it). Rate limited per client IP, counting only requests with the right key. |
| `DELETE /v1/rooms/{room}` | owner | `204`. Deletes the room and everything in it in one transaction: every file (shared and private), member, token and invite. Then every socket of the room closes with `4003`. A manager's invite whose token was checked just before the delete isn't stored (`401`), and a redeem needs the room, so no invite or token outlives it. From then on the room answers like one that never existed (`401`, redeem `404`), and its size, file count and connections no longer count anywhere. `403 owner_only` for anyone else. Shares a per-IP budget of 20 an hour with `members/me`, checked after the token. |
| `POST /v1/rooms/{room}/invites` | manager | Body `{"role":"player"\|"dm","manage":bool}` (optional: none or `{}` is a player). `201 {"invite","expires","role","manage"}`; `413 too_many_members` at 32 members plus pending invites; `400 bad_request` for `owner` or a managing player; `403 owner_only` when a manager asks for `manage`. |
| `GET /v1/rooms/{room}/invites` | manager | `200 [{"invite","expires","role","manage","member_id"?}]`, pending invites only (`member_id` on a re-invite). A manager doesn't get the ones that grant `manage` or re-invite a manager. |
| `DELETE /v1/rooms/{room}/invites/{invite}` | manager | `204`; `404 invite_not_found` when it isn't pending; `403 owner_only` for a manager and an invite that grants `manage` or re-invites a manager. |
| `POST /v1/rooms/{room}/invites/{invite}/redeem` | none | Body `{"member":"<display id>"}`. `201 {"token"}`; uses up the invite. A new member gets the invite's role; a re-invite makes the token that member (see Re-invite) and closes their old sockets with `4002`. `404 invite_not_found` (unknown or revoked invite, unknown room, or a re-invite whose member is gone or whose role or `manage` changed since), `410 invite_used`, `410 invite_expired`. Rate limited per client IP. |
| `GET /v1/rooms/{room}/members` | manager | `200 [{"member_id","member","role","manage","owner_is_dm","created","last_seen"}]`; `last_seen` (null until then) is bumped when a socket connects, `member` by `hello`. |
| `PATCH /v1/rooms/{room}/members/{member_id}` | owner | Body `{"role":"player"\|"dm","manage":bool}` (either may be left out), or on the owner's own row only `{"owner_is_dm":bool}`. `204`; the member's sockets get a new `access` at once. A player never manages. `400 cannot_change_owner` (a role or `manage` for the owner), `400 bad_request` (`owner`, `manage` for a player, or `owner_is_dm` for anyone but the owner), `404 not_found`. |
| `POST /v1/rooms/{room}/members/{member_id}/reinvite` | manager | `201 {"invite","expires","role","manage","member_id"}`, a re-invite (see above). `400 cannot_reinvite_owner`, `403 owner_only` (a manager and another manager), `404 not_found`. |
| `DELETE /v1/rooms/{room}/members/{member_id}` | manager | `204`; the token stops working at once, the member's sockets close (`4001`), their pending re-invites go, and their whole private space is deleted from the server (rows, not tombstones, with the room's size and file counts). DMs who read private notes get a new `access` without the member. `400 cannot_remove_owner`, `403 owner_only` (a manager and another manager), `404 not_found`. |
| `DELETE /v1/rooms/{room}/members/me` | any member but the owner | `204`: the caller leaves. As a removal: the token stops working, the member's sockets close (`4001`), their pending re-invites and whole private space go, and DMs who read private notes get a new `access`. `400 owner_cannot_leave` for the owner (who deletes the room instead). Rate limited with `DELETE /v1/rooms/{room}`. |
| `PATCH /v1/rooms/{room}/settings` | owner | Body `{"dm_reads_private":bool}`. `200` with the same body; every socket of the room gets a new `access`. |
| `GET /v1/rooms/{room}/changes?since=N` | any member | `200 {"seq","changes","more"}`, the same page as a replay batch (what this member may see, see "Who sees what"), without waiting. For scripts, debugging and tests; the app uses the socket. Shares the per-member read budget with socket upgrades. |
| `GET /v1/rooms/{room}/live` | any member | WebSocket, see above. |
| `GET /join/{room}/{invite}` | none | The invite page (static: it shows neither the room nor the invite and loads nothing). Its one script, allowed by hash, hands the link to the app (see "Opening an invite from the browser"); the CSP is otherwise `default-src 'none'` and forbids framing. It never touches the invite. |
| `GET /healthz` | none | `200 ok` (for the container healthcheck) |
| `GET /` | none | redirect to `https://yonatankarp.com/lorekeeper/` |

## Limits

Configurable by environment; defaults: blob 30 MiB (the decoded `nonce || ciphertext`; in base64 on the wire about 40 MiB, so frames are allowed the blob limit in base64 plus 64 KiB), room total 1 GiB of blobs, 20,000 files per room (tombstones don't count, but a new file is refused once the room holds twice that many files and tombstones together), 60 writes per minute per room, 32 connections per room and 64 on the whole server, room creation 5 per hour per IP, invite redemption 20 per hour per IP, 32 members plus pending invites per room. A room over a lowered limit can still shrink. Over a limit: `413` or `429` with `{"error": "..."}` over HTTP (`too_many_connections` on the upgrade), or an `error` frame on the socket.

Fixed, not configurable: 60 socket upgrades plus `GET /changes` per member per minute (each can read the whole room), 600 messages per socket per minute, 4 MiB of blobs per page of changes, 20 room deletions plus leaves per IP per hour. Per-IP limits count an IPv6 client as its /64, and each limit tracks at most 10,000 clients at once (past that, new clients get `429` until a window ends). Each member (all their devices together) can hold at most 8 sockets. There is no per-IP connection cap: a socket needs a token, so the per-member, per-room and server-wide caps bound what one party can hold.

**Memory:** a socket sending a page holds it about three times (the blobs, their base64, the JSON frame), and one receiving a `put` holds the frame about three times too. A page is at most 4 MiB of blobs unless a single blob is bigger, so the worst case is about 3 x the blob limit per busy socket: around 100 MB at the defaults, for example when one 30 MiB file fans out to every player at once. Size the container's memory for the largest files your party shares times the sockets that receive them at once, or lower `LOREKEEPER_SYNC_MAX_BLOB`.

The server logs no blobs, tokens, keys, invites, display ids or file ids: only its start, its shutdown and database errors.

| `LOREKEEPER_SYNC_INVITE_DAYS` | `7` | invite lifetime |
| limit overrides | | `LOREKEEPER_SYNC_MAX_BLOB`, `..._MAX_ROOM_BYTES` (bytes), `..._MAX_FILES`, `..._WRITES_PER_MINUTE`, `..._MAX_CONNECTIONS` (per room), `..._MAX_CONNECTIONS_TOTAL` (server-wide), `..._ROOMS_PER_HOUR`, `..._REDEEMS_PER_HOUR` |

Container: listens on 8080, data in the `/data` volume, runs as UID and GID 10001 (no home directory or passwd entry needed), writes nothing outside `/data` (so `read_only: true` works), healthcheck `lorekeeper-sync --healthcheck` (GETs `/healthz` on the port from `LOREKEEPER_SYNC_ADDR`, exit 0 or 1; the image has no shell or curl). Image: `ghcr.io/yonatankarp/lorekeeper-sync` (linux/amd64), tags `sha-<short commit>` and `latest` from main, built by `.github/workflows/sync-server.yml` when `sync-server/` or `sync-protocol/` change.

## Running your own sync server

```bash
openssl rand -base64 33 > create-key      # 44 characters; keep it private
docker volume create lorekeeper-sync
docker run -d --name lorekeeper-sync --restart unless-stopped \
  -p 8080:8080 -v lorekeeper-sync:/data \
  --read-only --tmpfs /tmp \
  -e LOREKEEPER_SYNC_PUBLIC_URL=https://sync.example.com \
  -e LOREKEEPER_SYNC_TRUST_PROXY=none \
  -e LOREKEEPER_SYNC_CREATE_KEY="$(cat create-key)" \
  ghcr.io/yonatankarp/lorekeeper-sync:latest
```

- Put it behind HTTPS (a reverse proxy, or a Cloudflare tunnel with `LOREKEEPER_SYNC_TRUST_PROXY=cloudflare`), and make sure the proxy passes WebSocket upgrades. Invite links only accept `https://` for anything but localhost.
- **`LOREKEEPER_SYNC_CREATE_KEY` is required.** The app is public, so without it anyone who knows the address could create rooms on your server and fill your disk. The owner enters the key once when creating a shared campaign; players joining with an invite never need it.
- Exposed directly (no proxy), the server has no header-read timeout, so slow clients can hold connections open; a reverse proxy or a Cloudflare tunnel in front takes care of that.
- With a bind mount instead of a named volume, make the directory writable by UID 10001 (`chown 10001:10001 /srv/lorekeeper-sync`).
- Back up the volume; `sync.db` with its `-wal` file is the whole state. It holds only encrypted data, but losing it means every player uploads again.
- In Lorekeeper, set **Settings > General > Advanced > Sync server** to your URL before sharing the campaign (players who join get the server from their invite link).

## Client behaviour (app)

The engine is `src-tauri/src/sync.rs`; it knows nothing of Tauri and is tested end to end against the real server in `sync_tests.rs`. `src-tauri/src/shared.rs` wires it to the app.

- **Settings and secrets:** per campaign, `sharing[<folder>]` holds `shared`, `me` (your PC's page, `PCs/<name>.md`, or `DM` for a DM who plays no character; see "The DM's author file"), `server`, `room`, `role` (`owner` or `member`: who made the room here, not the server role), `removed`, `replaced`, `unshared`, `access` and `privateNotice`. Only Share and Join set `server`, `room` and `role` (Stop sharing and Leave clear them); `removed`, `replaced` and `unshared` come from a removal, a re-invite or the owner stopping sharing; `access` (`memberId`, server `role`, `manage`, `dmReadsPrivate`) is what the server's last `access` message said, so every label about private notes follows the server. The settings window can't change any of them (`guard`), and can only clear `privateNotice`. The room key and the campaign's token are one keychain entry (`sync-room <room>`), and the server's creation key another (`sync-create-key <server origin>`), sent only to that server. Nothing secret goes into settings, state files, logs, events or error messages. The server for new shared campaigns is the **Sync server** setting, else `LOREKEEPER_SYNC_SERVER`, else `https://lorekeeper.yonatankarp.com`; any of them must pass `server_origin` (https, or http only for loopback).
- **Share** (owner): `POST /v1/rooms` with the creation key from the keychain; on `create_key_required` the window asks for it and Lorekeeper keeps it once it works. A new random key goes to the keychain with the owner token, and the campaign's name goes into `.lorekeeper/campaign.json` (`{"name": ...}`), the one hidden file that syncs, so joiners can name their folder. Then the first sync uploads everything.
- **Invite** (owner or manager): one-time invites as a player or a DM (`manage` for a DM, the owner's to grant), each link built with `Invite::link` only when asked for, shown once in a dialog (Copy copies; the dialog clears them on close or after 10 minutes). Pending invites can be cancelled, and players (names decrypted, role, last seen) removed or re-invited (the link shows like an invite). All of it is in the campaign's **Party…** dialog, which re-reads the invites and members while open: when the campaign's presence changes (a player who joins connects), and every 5 seconds, since the settings window gets no event when a member leaves (they go offline before the `DELETE`, and the engine reports `access` only when your own changes) or another manager invites; not while focus is in either list, and a refresh that fails keeps the lists shown. The owner changes roles there and, under Private notes, who reads them ("Private notes visible to: the player only / the player and the DM") and whether they're the DM themselves ("I'm the DM", `owner_is_dm`); everyone else sees their role and that setting read-only.
- **Join:** the pasted link is parsed (`Invite::parse`), the window shows its server (and warns when it isn't the default) and the player confirms. A re-invite joins the same way, on the new computer. Then redeem (display id "" until a PC is picked) and keep key and token in the keychain. Before making any folder, wait for the campaign's name (`wait_for_name`): read the replay for `campaign.json`, then live changes when the replay ended without it (the window then says "Waiting for the owner's notes to upload…"), pinging every 30 seconds and reconnecting when the connection drops, for up to a minute. The name is checked as a folder name (`folder_name`); a `campaign.json` whose name can't be one ends the wait at once. Without a usable name, the window asks for the folder's name and joins again with it (or, when no connection got through at all, says it can't reach the sync server); the invite isn't redeemed twice (the keychain already holds that room's token with the same key). Then make `<library>/<name>` (" 2" and so on when taken, or when it's one of the Lorekeeper folder's own folders such as `Templates`, in any case); no folder ever gets a stand-in name. The campaign is added with shared on and role member, which starts its engine and the download, and opened. The Join dialog shows the progress ("Joining <name>…", the engine's "Downloading N of M files…", "Done") from the `sync-join` events and the campaign's status, then asks which PC you play. The link is cleared from the dialog once joined. When the first `access` message says the redeemed invite's role is `dm` and no PC is picked yet, the app sets `me` to `DM` instead of asking (`dm_plays_no_character` in shared.rs); the player can still pick a PC.
- **Every shared campaign syncs**, open or not: one engine each (`shared::restart` keeps them matching the settings), with its own state file and its own status events, tagged with the campaign's folder. At most 8 run at once (`MAX_ENGINES`; each holds a connection, and the server allows 64 in all): the open campaign first, then in the list's order; the rest show "Waiting" until one stops or you open them. Switching campaigns reconnects nothing. Share starts the campaign's engine at once, so a campaign that isn't open uploads too. Choosing your PC restarts that campaign's engine, so `hello` carries the new display id; a restarted engine waits for the old one to end, so two never share a state file, and removing a joined campaign forgets its token and state only once its engine ended. Remote changes refresh the windows only for the open campaign.
- **Campaigns inside a campaign:** a campaign kept in the Lorekeeper folder itself (from before campaigns had folders of their own) holds the folder of every campaign made or joined since, and you may add a folder inside another campaign's. Their files are theirs: the outer campaign's engine is told which of its folders hold your other campaigns, listed, or removed from the list but once shared or named (`Config::nested`, compared case-folded) and never sends a file from them (their `Private/` notes included) nor writes one that arrives for them. A file it sent there before (older versions synced them) stays in its room until someone deletes it.
- **What syncs:** shared files, and your own private files (`Private/<path>`, see "Private notes"): Markdown pages and images (the app's list: png, jpg, jpeg, gif, webp, svg) under names that are safe on every system (no Windows-reserved names or characters, including `CON .md` and `COM¹`, no control characters, no trailing dot or space, at most 255 bytes a name and 1024 a path), plus `.lorekeeper/campaign.json`. Names that would read as another file or show as another name never sync either: a `~` followed by a digit (Windows may take `TEMPLA~1` for `Templates`) and bidi controls. Never: other hidden files and folders (`.obsidian`, `.trash`, `.DS_Store`), the top-level `Templates/` folder in any case (`templates/` and even `Templateſ/` are `Templates/` on macOS; Lorekeeper moves a campaign's templates into the shared Lorekeeper folder, which would read as deletions), a top-level folder that folds to `private` but isn't exactly `Private` (folding case, and the invisible characters HFS+ skips when it compares names, such as U+200C and U+FEFF, which also count for hidden names and `Templates/`; so a shared path from another player can never land in your private notes on a case-insensitive disk, and a `private/` folder of yours never syncs at all), `.lorekeeper/dm/` (a DM's copies), sync conflict copies (the named patterns `syncConflicts` in vault.js flags), symlinks, files over about 22 MB (a warning), or anything outside the campaign folder. The same check applies to every path that arrives.
- **State:** `<config>/sync/<room>.json`, written atomically, at most once a second while connected and when a connection ends: the room's last `seq` (from `changes` and `change` only, never from an `ack`), `path -> {id, seq, hash, len, gone}` by local path (`Private/...` and `.lorekeeper/dm/...` included), your `member_id` (your private files' ids are made with it) and `dm` (you hold every private note you may read up to `seq`). A state file that's damaged or doesn't fit the key (or whose private ids don't fit its member id) means a fresh catch-up: local files are compared by hash and never deleted.
- **Connect:** `Authorization: Bearer` on the upgrade (wss with rustls and the Mozilla roots, ws only for loopback), frames capped at the server's limit; a message the server doesn't take within 30 seconds plus 64 KiB a second of its size means the connection is gone. `hello` with the last `seq` (and `dm_since: 0` until `dm` is set, so a DM who gained access while offline gets every private note; the server sends none to anyone else), apply the replay pages (`more: true` loops), then push. A ping every 30 seconds; nothing heard for 75 seconds (sleep, a dead network) means reconnect. Reconnects back off from 1 second, doubling to a minute; only a connection that lasted a minute starts over, so a server that keeps closing or refusing (the per-member connection budget) isn't hammered. `401` on the upgrade or close code `4001` mean removed, `4002` signed in on another computer (a re-invite), `4003` the owner stopped sharing: that campaign's sync stops for good, the campaign is marked no longer synced (with `replaced` for `4002`, so the window says "Signed in on another computer", and `unshared` for `4003`, so it says "The owner stopped sharing <name>. Your copy stays on this computer.", also as a notification), its token, state and DM copies are deleted, and the files stay. A member who was offline when the room was deleted gets `401` on their next connection and sees "Removed" instead (unknown rooms and revoked tokens look the same, by design). A computer that was offline when its member was re-invited gets `401` on its next connection and says "Removed". The owner can't be removed or re-invited, and stops sharing from their own computer, so for them any of these is a server problem (or a hostile one): it only stops sync with a message, and the key and owner token stay.
- **Push:** the 3-second folder watch (which sees the app's own writes too) looks at every campaign that syncs (sizes and times only) and pokes that campaign's engine, which compares each file's hash with the state (sizes and times cached, so unchanged files aren't read again). A changed file is a `put` with `base` = its last seen `seq`; a deleted one an encrypted tombstone. A private file goes up as `space: "private"` with its private id and the path inside `Private/` in its blob, and only once this connection's server sent `access`: a server that doesn't know private spaces would store it as shared. DM copies never go up, and their absence is never a deletion. At most 4 writes are in flight; `rate_limited` pauses 20 seconds and keeps the queue; `too_large` and other refusals skip that version with a warning; `room_full` and `too_many_files` stop pushing and say so. After a `conflict` the next push builds on the returned version even when it can't be applied; a path that conflicts 5 times without an ack waits for the next connection. If the campaign folder is missing, or its synced `campaign.json` is gone, deletions aren't pushed: an unmounted drive must never delete everyone's files.
- **Pull:** for each change, a version already applied (`seq` not above the one seen for that id) is skipped, so a live change and a `conflict` reply for the same version count once. A blob is decrypted and checked (`open` checks path and id, `open_private` the same for the change's `author`; then the path must sync). A private change of yours lands in `Private/<path>`, another member's in `.lorekeeper/dm/<author>/<path>` only while `access` says you read them (otherwise it's dropped, whatever the server sends), anything else is dropped. If the local file is unchanged since it last synced (or absent), the new content is written through a temporary file (a short hidden name of its own) and a rename in its folder, after checking that no folder on the way and not the target is a symlink and that the result stays under the campaign folder. If it also changed locally, the local file stays and the incoming version is saved beside it as `<name> (conflict <date> <time>).<ext>` (a counter when taken, created with `create_new`), which Home's Sync conflicts card lists; the local version then goes up over it. A conflict copy's name is cut to 255 bytes at the end of its stem. A change whose name this computer can't hold (a path past macOS's 1024 bytes with the campaign folder in front) is skipped with a warning instead of retried, so one such file can't stop sync; so is one whose path goes through a file (`Page.md/x.md`). A tombstone moves an unchanged file into the campaign's hidden `.trash` folder, never through a symlink (a changed one stays and goes up again); `campaign.json` is never deleted. Nothing empties `.trash`. Writes are recorded as the app's own, so the folder watch doesn't report them, and the windows refresh.
- **Untrusted versions:** a server-side delete (null blob) or a blob that doesn't open never touches local files; the player gets a warning, and the local version goes back up over it, which repairs the room for everyone. Such a version for a file this computer doesn't have is dropped without a trace, and presence keeps at most 64 names, so a hostile server can't grow memory. What a hostile server can still do: withhold changes, replay an older version a player once wrote (blobs carry no version), and close or refuse connections.
- **Limits:** more than 20,000 files or 1 GiB in a room, more than 4 GiB written or 500 conflict copies in one run stop sync with a message, so a hostile server can't fill the disk.
- **Status** (events to the windows and on the campaign in Settings and the sidebar): "Connecting", "Downloading N of M files" while catching up (N counts the replay's changes as they're applied, reported at most every 250 ms and at the end of each batch; "Downloading N files" from a server that sends no `total`), "Syncing" or "Syncing N", "Synced", "Waiting" (past the 8 campaigns that sync at once), "Offline, will sync when the server is back", "Removed from this campaign", "Signed in on another computer", "The owner stopped sharing <name>", or "Sync stopped" with the reason. **Presence:** the names from `presence`, decrypted, without your own entry (told apart by your sealed display id).
- **Files on disk:** reads use `O_NOFOLLOW` on Unix and `FILE_FLAG_OPEN_REPARSE_POINT` on Windows (a symlink or junction is refused), after checking every folder on the way. A folder swapped for a symlink between that check and the read or write is the one race left; it needs someone already on this computer. Hard links aren't detected.
- **Leaving:** removing a joined campaign from Lorekeeper deletes its token and state (the server still lists the member). The owner's secrets stay when they remove their own campaign: they're the only way to invite or remove players.
- **Leave** (Party dialog, anyone but the owner, after a confirmation) and **Stop sharing** (the owner, after a confirmation naming the campaign): only from the Settings window (the main window shows the party's notes, so it can't ask): that campaign's engine (one of the engines that run, one per shared campaign) stops first and is waited for (`stop_for`), so it can't see the room close or write its state after the cleanup; one still busy after 10 seconds (a big upload) is waited for before the keychain entry, state file and DM copies go, and any later engine for that campaign starts only once it ended. Then `DELETE /v1/rooms/{room}/members/me` or `DELETE /v1/rooms/{room}`; a refusal shows its message and sync starts again, and `401` counts as done (already gone). Then the campaign becomes local-only (not shared, no server, room or role; your PC choice stays), and its keychain entry, state file and DM copies are deleted. The files stay. Players' engines get `4001` (Leave, on the leaver's other devices) or `4003` (Stop sharing).
- **Delete campaign** (Settings, under Rename or remove, next to Remove from list, after a confirmation naming the folder): stops that campaign's engine and waits for it (any shared campaign may be syncing), then deletes other members' private notes in it (a DM's copies, which aren't yours to keep, even in the Trash), moves the campaign's folder to the system Trash (the `trash` crate, as for pages) and takes it off the list, which leaves a joined campaign's room as removing it does (its token and state go once the list is saved). If the engine is still busy after 10 seconds, or the move fails, nothing is deleted and the engine starts again. Only the Settings window can ask for it. Refused for the open campaign (hidden there, as Remove from list is), anything but a real folder (a symlink to one), the Lorekeeper folder, its `Templates/`, a folder holding either of them, the home folder or the backup folder, and a folder holding another listed campaign; paths are compared canonical and case-folded. For a campaign you share, the dialog offers **Stop sharing and delete** first, or **Delete only**, which leaves the room on the server with its owner token in the keychain.
- **Renames:** ids come from paths, so a rename (or a move to another folder) syncs as a new file plus a tombstone for the old path. Making a page private or shared (moving it into or out of `Private/`) is the same: a tombstone in one space and a new file in the other; the app's Move refuses to cross that line, so it only happens through Make private or Make shared, which ask first. Making a shared page private takes nothing back: the server keeps only the tombstone, but players who synced the page keep what they got (moved to their `.trash`), and the app says so.
- **Per-player session files** mean the common case, everyone writing notes during a game, never conflicts.
- **The DM's author file:** a DM who plays no character ("I play: I'm the DM (no character)", `me` = `DM`, `DM_ME` in lib.rs) writes `Sessions/Session N/DM.md`, and private notes to `Private/Sessions/Session N/DM.md`, with the property `author: DM` instead of a link to a PC page. The display id is `DM` sealed like any name, so presence, the Players list and "Online: ..." show "DM", and the timeline and journal label those notes "DM" without a link or portrait (`authorLink` in notes.js), even if a `PCs/DM.md` page exists. The stem is reserved: `validate` refuses a PC page whose name folds to `dm` (`PCs/DM.md`, `PCs/dm.md`) as `me`, since on a case-insensitive disk it would write the same file. Two DMs without a character share `DM.md` and can conflict. Only the owner (also while sharing it for the first time) and a member whose `access` role is `dm` are offered `DM` (`mayPlayDm` in vault.js); a member whose `access` role is `player` with `me` = `DM` (picked before, or kept from being a DM) has `me` cleared on every `access` message, unchanged ones too (`a_player_plays_a_character` in shared.rs), and the windows treat it as no PC picked until then (`myPc`). Picking `DM` doesn't make anyone read private notes: that's the server's role, and for the owner the separate `owner_is_dm` switch, which the Party dialog suggests when the owner picks `DM`.

## Private notes

A member's private notes are the top-level `Private/` folder of their campaign folder (exactly that name), laid out like the rest: `Private/NPCs/Halia.md`, `Private/Sessions/Session 4/Sibling 5.md`. They're ordinary files there, so normal Lorekeeper backups include them, and Obsidian can open them.

- **Sync, by access control, not extra crypto.** Private files are encrypted with the room key like everything else (no personal keys, no recovery codes). The server keeps them in the author's private space, keyed by `(member_id, id)`, and delivers them only to the author's own connections (all their computers) and, while the room's `dm_reads_private` is on, to DMs (and an owner who said they're the DM). Never to anyone else, the owner included: not live, not in a replay, not over `GET /changes`, not in a conflict reply (a conflict only ever holds the writer's own file), and not in `presence` or any error. Every member holds the room key, so this is the server keeping its word: see the threat model below.
- **Who reads them** (`Role::reads_private`, the one rule for the server's delivery and the app's labels): only you, or you and the DM, where "the DM" is whoever holds a DM's reading right: members with the `dm` role, and the owner only after turning on "I'm the DM". Every place that offers or shows a private note says which: "Private: only you" or "Private: you and the DM", from the server's last `access` message (before the first one, a joined campaign says "you and the DM": its notes go up once it connects, and the room may allow it). When the setting changes, members get a one-time notice in the main window.
- **The app:** a **Private** group with a padlock in the sidebar; padlocks in search results and the page header; a **Private** switch in New page (in a shared campaign); **Make private** / **Make shared** in the page header (sharing asks first, and undo or redo never shares a page); and a quick note starting with `~` goes to `Private/Sessions/Session N/<PC>.md`, the shared session's number, without making the shared file (the `~` goes, other prefixes still file it: `~@Halia lies` is a private NPC note; `↑` never turns a shared note private in place, it saves a new private note). A session page merges your private notes into its timeline and journal, with a padlock, but never into its searchable text. Links to private pages resolve for you like any page; making a page private or shared rewrites no links (they find it by name, and a shared page must not learn a private path), and renaming a private page rewrites links only in private pages.
- **A DM's copies:** a DM who may read private notes gets each player's as read-only copies in `.lorekeeper/dm/<member id>/<path>` (named by the validated member id, never a display id), plus `.lorekeeper/dm/players.json` with the players' PC names (from `access`, and from `presence` for a player who named their PC after joining). Images in a player's private notes are copied too, but the window doesn't show them yet. They're hidden, so they never sync back, never get backed up and Obsidian skips them; the sidebar shows them under **Players' private notes**, a folder per player, and session pages merge them with author and padlock. The app can't edit, rename or delete them (`vault_file` refuses `.lorekeeper/`), and an edit made outside it is overwritten by the player's next version. When access ends (the setting off, a demotion, removal, re-invite, leaving the campaign), the copies are deleted at once, and a member who's gone from `access.members` loses their folder.
- **Removal** and **Leave** delete the member's whole private space from the server, and **Stop sharing** every member's; a re-invite keeps it (the member id carries over). A hostile server can claim any of these (`4001`, `4003`, `401`) to stop a member syncing, as it can refuse connections anyway; the member's files stay.
- **What the server can do:** it stores private notes encrypted and can't read them; its operator could, in principle, read the database (still encrypted), or run a modified server that sends private blobs to other members, who hold the room key and could then read them. The app refuses another member's private file unless the server said it may read them, but a modified server can lie about that too. The owner and managers can take over a member through a re-invite (the member sees "Signed in on another computer"), and decide who is a DM (managers can invite DMs; the owner can make anyone one, and themselves the DM). Members learn a little about others' private notes without reading them: `seq` gaps show that someone wrote one and when, and the room's size limit (`room_full`) shows the room's total, private files included. A member can fill the room's limits with private files nobody else sees; removing them frees the space. Turning the setting off stops delivery and deletes the DM's copies at their next connection; nothing can recall a copy someone already made elsewhere.
